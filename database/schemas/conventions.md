# Conventions

The rules every table follows. Deviations are called out in the table's own file.

| Concern | Rule |
| ------- | ---- |
| Primary key | `uuid` v7, named `id`, generated by `uuidv7()`, never reused |
| Document key | `doc_id` is a UUID v5 derived from the canonical URL (`lynx_common::ids::DocumentId`), so re-crawls update in place |
| Timestamps | `timestamptz`, always UTC; `created_at` / `updated_at` on every mutable table, maintained by the `set_updated_at` trigger |
| Enums | Postgres `enum` types for closed sets (`crawl_state`, `document_state`, `error_class`, `ban_scope`, `discovery_source`, `retention_class`); extending one requires an `ALTER TYPE ... ADD VALUE` migration |
| Nullability | `NOT NULL` by default; a nullable column means "unknown" and is documented |
| Free text | `text` only; no `varchar(n)` guessing |
| JSON | `jsonb` only for variable-shape data, with a documented shape |
| Soft delete | Only where history matters (`url`, `document`, `abuse_report`); `DELETE` elsewhere |
| Money | Not applicable in v0.1 |

## Logical references vs. foreign keys

Foreign keys are added deliberately. Three hot paths use a **logical reference**
(a `uuid` column with no FK) rather than a hard FK, to keep write contention
predictable; integrity is enforced by the reconciliation job:

| Column | Reference | Why not a FK |
| ------ | --------- | ------------ |
| `crawl_frontier.url_id` | `url(id)` | hottest write path in the system |
| `crawl_frontier.host_id`, `crawl_attempt.host_id` | `host(id)` | claim path must not join |
| `document.url_id` | `url(id)` | bulk indexer writes |
| `link.source_doc_id` | `document(doc_id)` | bulk link writes |
| `admin_audit_log.admin_user_id` | `admin_user(id)` | audit must survive identity migration |

Every other relation has a real FK, and URL-derived rows use `ON DELETE CASCADE`
so deleting a URL cannot orphan work.

## Identifiers

- Entities (`domain`, `host`, `url`, `api_key`, clusters, manifests rows) use
  **UUID v7**: time-ordered, so B-tree inserts stay local and are not enumerable
  the way a sequential integer is.
- Documents use a **UUID v5** derived from the canonical URL, so identity is
  reproducible across processes and restarts. `doc_id` is the join key into
  Tantivy; a mismatch between the two systems is corruption, not a merge case.
- Bigint identity columns are used only for high-volume append-only logs
  (`link`, `crawl_attempt`, `admin_audit_log`).

## Partitioning

Range-partitioned by month, so retention is `DROP PARTITION` rather than `DELETE`
and vacuum stays predictable:

- `crawl_frontier` by `created_at`
- `crawl_attempt` by `started_at`

Each has a `DEFAULT` partition so an insert never fails before the next month's
partition exists. A partitioned table's primary key includes the partition key,
which is why those tables key on `(id, created_at)` / `(url_id, created_at)`.

`link` and `document_version` are **not** partitioned in v0.1. Range partitioning
by time would conflict with their natural primary keys, and hash partitioning
would complicate the expand/contract path; both are recorded as scale steps rather
than built speculatively.

## Personal data

Only two tables may contain personal data: `abuse_report` and `api_key` (owner
email). Both store it field-level encrypted, with an HMAC lookup hash as the only
queryable form. No table may contain a search query; there is no column for one,
and adding one is prohibited without an ADR.

## Naming resolution

This directory is the physical schema. Where prose elsewhere in `docs/` uses older
names, the mapping is:

| Prose name (`docs/database/schema.md`) | Physical name (here) |
| -------------------------------------- | -------------------- |
| `crawl_host` | `host` (plus `domain`) |
| `frontier` | `crawl_frontier` |
| `robots_cache` | `robots_policy` |
| `cluster` / `dedup_signature` | `dedup_cluster` |
| `crawl_log` | `crawl_attempt` / `crawl_stat_daily` |
| `tombstone` | `takedown_request` |
| `quality_label` | `relevance_judgement` |

The physical names are authoritative because they are what `services/storage`, the
migrations, and `packages/models` agree on.
